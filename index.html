1. Why virtual threads exist

Most server code is written thread-per-request: one thread handles one request from start to finish, and when it calls a database or another service it simply waits. That style is easy to read, debug and profile. Its problem is cost. A platform thread is a thin wrapper around an operating-system thread, with a large reserved stack and a kernel scheduling entry, so a JVM can only afford a few thousand of them. SOURCED

Little's law ties that limit to throughput. If each request spends W seconds in the system and you want λ requests per second, you need L = λ × W requests in flight at once, and with thread-per-request each one holds a thread. A 200-thread pool serving requests that wait 100 ms can never exceed 2,000 requests per second, no matter how idle the CPU is.

The industry's previous answer was asynchronous code (callbacks, CompletableFuture chains, reactive streams), which frees the thread during waits but gives up readable stack traces and straight-line control flow. Virtual threads, final in JDK 21 (JEP 444), keep the thread-per-request style and make the threads cheap enough to have millions. SOURCED

2. The mental model

A virtual thread is a java.lang.Thread whose stack lives on the heap as a continuation. The JDK runs it by mounting it on a platform thread called a carrier. Carriers come from a small ForkJoinPool, one per core by default. SOURCED

  1. Mount. The scheduler picks a runnable virtual thread and copies the top of its stack onto a free carrier.
  2. Run. Your code executes on the carrier like any other Java code.
  3. Block → unmount. When the code blocks in a JDK API that supports it (socket read, Thread.sleep, BlockingQueue.take, lock acquisition), the virtual thread saves its stack frames to the heap and gives the carrier back. The carrier immediately runs someone else.
  4. Unblock → remount. When the I/O completes, the virtual thread becomes runnable again and is mounted on whichever carrier is free, possibly a different one.
The one-sentence version: virtual threads make waiting cheap. They do not make computing faster, and they are not time-sliced: a virtual thread that never blocks keeps its carrier until it finishes. SOURCED

The exceptions to step 3 are what the rest of this page is about. When a virtual thread blocks but cannot unmount, it is pinned, and its carrier sits idle with it. Which situations pin has changed across JDK releases (section 6).

3. The API in five minutes

There is no new thread class to learn. A virtual thread is a Thread; you just create it differently.

// L1: three ways to start a virtual thread, and what one looks like.
public class L1Hello {
    public static void main(String[] args) throws Exception {
        Thread a = Thread.ofVirtual().name("vt-a").start(() ->
            System.out.println("a: " + Thread.currentThread()));
        Thread b = Thread.startVirtualThread(() ->
            System.out.println("b: isVirtual=" + Thread.currentThread().isVirtual()));
        try (var exec = java.util.concurrent.Executors.newVirtualThreadPerTaskExecutor()) {
            exec.submit(() -> System.out.println("c: daemon=" + Thread.currentThread().isDaemon()));
        } // close() waits for submitted tasks
        a.join(); b.join();
        System.out.println("main: " + Thread.currentThread() + " isVirtual=" + Thread.currentThread().isVirtual());
    }
}

Lab 2 · 10,000 tasks that each wait 100 ms MEASURED

// L2: 10,000 tasks that each block for 100 ms.
// Platform pool of 200 vs one virtual thread per task.
import java.time.*; import java.util.concurrent.*; import java.util.stream.*;
public class L2Scale {
    static final int TASKS = 10_000;
    static void run(String label, ExecutorService exec) {
        Instant t0 = Instant.now();
        try (exec) {
            IntStream.range(0, TASKS).forEach(i -> exec.submit(() -> {
                Thread.sleep(Duration.ofMillis(100)); // stands in for a blocking DB/HTTP call
                return i;
            }));
        }
        System.out.printf("%-34s %6d ms%n", label, Duration.between(t0, Instant.now()).toMillis());
    }
    public static void main(String[] args) {
        run("fixed pool, 200 platform threads", Executors.newFixedThreadPool(200));
        run("virtual thread per task", Executors.newVirtualThreadPerTaskExecutor());
        System.out.println("Little's law: 10,000 tasks x 0.1 s / 200 threads = 5 s floor for the pool");
    }
}

// L3: CPU-bound work gets no speedup from virtual threads (warm up the JIT first).
import java.time.*; import java.util.concurrent.*; import java.util.*;
public class L3Cpu {
    static long burn(long n) { long x = 0; for (long i = 0; i < n; i++) x += (i * 31) ^ (x >>> 3); return x; }
    static long run(ExecutorService exec, int tasks) throws Exception {
        Instant t0 = Instant.now(); List<Future<Long>> fs = new ArrayList<>();
        try (exec) { for (int i = 0; i < tasks; i++) fs.add(exec.submit(() -> burn(50_000_000L))); }
        long sink = 0; for (var f : fs) sink ^= f.get();
        if (sink == 42) System.out.print("");
        return Duration.between(t0, Instant.now()).toMillis();
    }
    public static void main(String[] args) throws Exception {
        int cores = Runtime.getRuntime().availableProcessors(), tasks = cores * 4;
        for (int i = 0; i < 3; i++) run(Executors.newFixedThreadPool(cores), tasks); // warm-up
        System.out.println("cores=" + cores + ", tasks=" + tasks + " (each round, after warm-up)");
        for (int round = 1; round <= 3; round++) {
            long p = run(Executors.newFixedThreadPool(cores), tasks);
            long v = run(Executors.newVirtualThreadPerTaskExecutor(), tasks);
            System.out.printf("round %d: platform pool %4d ms | virtual per task %4d ms%n", round, p, v);
        }
    }
}
$ java L3Cpu.java  (JDK 25)
cores=2, tasks=8 (each round, after warm-up)
round 1: platform pool  150 ms | virtual per task  154 ms
round 2: platform pool  173 ms | virtual per task  161 ms
round 3: platform pool  158 ms | virtual per task  163 ms

No difference: two cores are two cores. A first version of this lab without the warm-up loop showed virtual threads "2.3× faster" because the pool ran first and paid the JIT's warm-up cost. That is a good story to tell students about benchmarking (see exercise 2).

Good fit

Many concurrent tasks that mostly wait: HTTP handlers, calls to databases and other services, message consumers, fan-out to several backends, blocking SDKs you can't rewrite.

No gain

CPU-bound work (use a pool sized to the cores, or parallel streams), a few long-lived threads, and code that's already non-blocking end to end. Reactive code gains little from switching. INFERRED

6. Pinning, and how it changed by JDK version

In JDK 21–23 a virtual thread could not unmount while it held a monitor (inside a synchronized block or method) or while it was inside a native frame. Blocking there held the carrier for the whole wait. With the default number of carriers equal to cores, a handful of such waits could stall an entire service. JEP 491 in JDK 24 reimplemented monitors so virtual threads can block inside synchronized and still unmount. Native frames, including FFM downcalls, and some class-initialization paths still pin. SOURCED

// L4: blocking inside synchronized. Run with -Djdk.virtualThreadScheduler.parallelism=1
// JDK 21: the virtual thread pins its carrier, so the 4 sleeps run one after another.
// JDK 24+: JEP 491 lets it unmount, so the sleeps overlap.
import java.time.*; import java.util.concurrent.*;
public class L4Pinning {
    public static void main(String[] args) {
        Instant t0 = Instant.now();
        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 4; i++) {
                Object lock = new Object();          // a separate lock per task: no contention
                exec.submit(() -> {
                    synchronized (lock) {
                        Thread.sleep(200);           // blocking while holding a monitor
                    }
                    return null;
                });
            }
        }
        System.out.println(Runtime.version().feature() + ": 4 x 200 ms in synchronized took "
            + Duration.between(t0, Instant.now()).toMillis() + " ms");
    }
}

7. Limiting concurrency: semaphores, not pools

A thread pool used to do two jobs: reuse expensive threads and cap how many things run at once. Virtual threads remove the first reason entirely, so never pool virtual threads. The second reason still matters: your database has a connection limit and the payment API has a rate limit. Express that limit directly at the resource with a Semaphore. SOURCED

Lab 6 · 200 tasks, a downstream that allows 10 MEASURED

// L6: limit concurrency to a fragile downstream with a Semaphore, not a pool.
import java.time.*; import java.util.concurrent.*; import java.util.concurrent.atomic.*;
public class L6Semaphore {
    static final Semaphore permits = new Semaphore(10);   // downstream allows 10 at once
    static final AtomicInteger inFlight = new AtomicInteger(), peak = new AtomicInteger();
    static String callDownstream(int i) throws InterruptedException {
        permits.acquire();
        try {
            int now = inFlight.incrementAndGet();
            peak.accumulateAndGet(now, Math::max);
            Thread.sleep(50);
            return "ok" + i;
        } finally { inFlight.decrementAndGet(); permits.release(); }
    }
    public static void main(String[] args) {
        Instant t0 = Instant.now();
        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 200; i++) { int n = i; exec.submit(() -> callDownstream(n)); }
        }
        System.out.println("200 calls, peak concurrency " + peak.get() + ", took "
            + Duration.between(t0, Instant.now()).toMillis() + " ms (floor 200/10 x 50 = 1000 ms)");
    }
}
$ java L6Semaphore.java  (JDK 25)
200 calls, peak concurrency 10, took 1016 ms (floor 200/10 x 50 = 1000 ms)

The same idea applies to connection pools. With 200 platform threads, a 10-connection pool saw at most 200 waiters. With 10,000 virtual threads it sees 10,000, all waiting on the pool. The bottleneck moves to the pool and its timeouts, so size it and set its acquisition timeout deliberately. INFERRED

8. Request context: ThreadLocal vs ScopedValue

ThreadLocal works on virtual threads, but it was designed for a few long-lived pooled threads. With a million short-lived threads, per-thread caches (the classic "cache an expensive formatter in a ThreadLocal" trick) are created a million times and never reused. Inheritable thread-locals copy the map into each child. ScopedValue is the replacement for passing context down a call: immutable, bound for a block of code, automatically unbound at the end, and cheap to inherit into structured subtasks. SOURCED

Lab 7 · ScopedValue MEASURED

// L7: ScopedValue (final in JDK 25, JEP 506) instead of ThreadLocal for request context.
public class L7Scoped {
    static final ScopedValue<String> USER = ScopedValue.newInstance();
    static void handle() { audit(); }
    static void audit() {
        System.out.println("audit: user=" + (USER.isBound() ? USER.get() : "<unbound>")
            + " on " + (Thread.currentThread().isVirtual() ? "virtual" : "platform") + " thread");
    }
    public static void main(String[] args) throws Exception {
        Thread t = Thread.ofVirtual().start(() ->
            ScopedValue.where(USER, "alice").run(L7Scoped::handle));
        t.join();
        audit(); // outside the scope: unbound, nothing to clean up, nothing leaked
    }
}
$ java L7Scoped.java  (JDK 25, no preview flag)
audit: user=alice on virtual thread
audit: user=<unbound> on platform thread

9. Structured concurrency (still preview)

Cheap threads make it easy to fork lots of work, and easy to leak it: a subtask that outlives its caller, or a failure in one branch while the others keep running. StructuredTaskScope ties forked subtasks to a lexical block. The block can't exit until they finish, a failure cancels the siblings, and thread dumps show the parent–child tree. SOURCED

Lab 8 · Fork two calls, fail fast MEASURED

// L8: structured concurrency (PREVIEW). Compile/run with --enable-preview on the JDK it was written for.
import java.util.concurrent.StructuredTaskScope;
import java.time.*;
public class L8Structured {
    static String user(int id) throws InterruptedException { Thread.sleep(100); return "user" + id; }
    static String orders(int id) throws InterruptedException { Thread.sleep(150); return "3 orders"; }
    static String failing(int id) throws InterruptedException { Thread.sleep(50); throw new IllegalStateException("inventory down"); }

    public static void main(String[] args) throws Exception {
        Instant t0 = Instant.now();
        try (var scope = StructuredTaskScope.open()) {      // default joiner: all succeed or fail fast
            var u = scope.fork(() -> user(42));
            var o = scope.fork(() -> orders(42));
            scope.join();
            System.out.println(u.get() + ", " + o.get() + " in " + Duration.between(t0, Instant.now()).toMillis() + " ms");
        }
        t0 = Instant.now();
        try (var scope = StructuredTaskScope.open()) {
            scope.fork(() -> orders(42));
            scope.fork(() -> failing(42));
            scope.join();
        } catch (StructuredTaskScope.FailedException e) {
            System.out.println("failed fast after " + Duration.between(t0, Instant.now()).toMillis()
                + " ms: " + e.getCause().getMessage() + " (sibling cancelled)");
        }
    }
}

11. Using them in production

Spring Boot

From Spring Boot 3.2 on Java 21+, one property moves request handling (embedded Tomcat or Jetty) and the auto-configured async executor and scheduler onto virtual threads: SOURCED

spring.threads.virtual.enabled=true

When it's on, pool-sizing properties for those executors are ignored, because there's no pool. The limits you used to get from server.tomcat.threads.max now have to come from the resources themselves: connection pool size, semaphores, rate limiters. SOURCED INFERRED

Migration checklist

  1. Get on JDK 25 if you can. You get JEP 491 (no synchronized pinning) and final ScopedValue in an LTS.
  2. Measure before switching: requests in flight, pool saturation, p99 latency. If threads were never your bottleneck, nothing will improve.
  3. Turn them on for I/O-bound entry points (the Spring property, or newVirtualThreadPerTaskExecutor where you own the executor).
  4. Replace pool-as-limiter with semaphores at the scarce resource. Delete pools of virtual threads.
  5. Audit ThreadLocal caches: per-thread formatters, buffers, and connection holders. Move request context to ScopedValue on 25.
  6. Load-test with JFR on and alert on jdk.VirtualThreadPinned. On 21, expect hits in synchronized and fix the hot ones; on 25, any hit is a native frame.
  7. Keep CPU-heavy work on a bounded platform pool so it can't monopolize carriers.

12. GET requests: for loop vs CompletableFuture vs virtual threads

This is the comparison most teams actually need: a handler has to make a batch of outbound GET calls and forward the caller's identity on every one. The benchmark runs the same job eight ways, on three JDKs in the cloud and two JDKs on the Windows desktop, and checks every response to confirm the headers arrived. MEASURED

The workload

  • N tasks (200 or 1,000). Each task calls GET /item/{i}, then a dependent GET /item/{i}/price, so a run makes 2N calls.
  • A local echo server in its own JVM waits 20 ms per request, standing in for a real backend. It sends back the headers it received.
  • Context forwarded on every call: X-Request-Id, X-Tenant-Id, Authorization: Bearer … and a W3C traceparent (same trace ID, new span ID per call). A call counts as forwarded only if the server echoed all four.
  • Timing: one warm-up run, then the median of three runs. Peak platform threads come from ThreadMXBean, which doesn't count virtual threads.
  • Same bytecode on every JDK: the core benchmark is compiled once with --release 21. The ScopedValue variant is compiled per JDK because StructuredTaskScope is still preview.

With perfect concurrency a task takes about 2 × 20 = 40 ms, so the best possible time for any N is roughly 40 ms plus overhead. In practice the floor is set by how fast the machine can push 400 or 2,000 HTTP exchanges through one client and one server.

// Local test server: waits LATENCY ms per request (stands in for a real backend),
// then echoes back the headers it received so the client can verify forwarding.
import com.sun.net.httpserver.*;
import java.net.*;
import java.nio.charset.StandardCharsets;
import java.util.concurrent.*;

public class EchoServer {
    public static void main(String[] args) throws Exception {
        int port = Integer.parseInt(args[0]);
        long latencyMs = Long.parseLong(args[1]);
        HttpServer server = HttpServer.create(new InetSocketAddress(InetAddress.getLoopbackAddress(), port), 8192);
        server.setExecutor(Executors.newVirtualThreadPerTaskExecutor()); // server must never be the bottleneck
        server.createContext("/item", ex -> {
            try { Thread.sleep(latencyMs); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            Headers h = ex.getRequestHeaders();
            String body = "rid=" + h.getFirst("X-Request-Id")
                    + "|tenant=" + h.getFirst("X-Tenant-Id")
                    + "|auth=" + h.getFirst("Authorization")
                    + "|tp=" + h.getFirst("traceparent")
                    + "|path=" + ex.getRequestURI().getPath();
            byte[] bytes = body.getBytes(StandardCharsets.UTF_8);
            ex.sendResponseHeaders(200, bytes.length);
            try (var out = ex.getResponseBody()) { out.write(bytes); }
        });
        server.start();
        System.out.println("listening on " + port + " with " + latencyMs + " ms latency");
    }
}

bench/GetBench.java

// GET benchmark: N tasks, each = GET /item/{i} then a dependent GET /item/{i}/price.
// Every outbound call must forward the inbound request's context as headers:
//   X-Request-Id, X-Tenant-Id, Authorization, and a W3C traceparent (same trace, new span per call).
// The server echoes what it received; every response is checked.
//
// Usage: java GetBench <port> <method> <n> <mode> <runs>
//   method: loop | cf-async | cf-pool | cf-common | vt | vt-vtclient | vt-sync
//   mode:   explicit    - capture the context in a local variable before fanning out (correct pattern)
//           threadlocal - read a ThreadLocal wherever the request is built (the common naive pattern)
// Compiled with --release 21 so JDK 21, 25 and 27 run identical bytecode.
import java.lang.management.*;
import java.net.URI;
import java.net.http.*;
import java.time.Duration;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class GetBench {
    /** The inbound request's context: what an incoming HTTP request handed us. */
    record Ctx(String requestId, String tenant, String bearer, String traceId) {}

    static final ThreadLocal<Ctx> CURRENT = new ThreadLocal<>();   // how most code "remembers" the request
    static HttpClient CLIENT;   // built in main; "vt-vtclient" gives the client a virtual-thread executor
    static String base;
    static String mode;

    /** Build an outbound GET that forwards the context. ctx may be null if it was lost. */
    static HttpRequest get(Ctx ctx, int i, String suffix) {
        var b = HttpRequest.newBuilder(URI.create(base + "/item/" + i + suffix))
                .timeout(Duration.ofSeconds(60)).GET();
        if (ctx != null) {
            String spanId = String.format("%016x", (long) i * 2 + (suffix.isEmpty() ? 0 : 1) + 1);
            b.header("X-Request-Id", ctx.requestId())
             .header("X-Tenant-Id", ctx.tenant())
             .header("Authorization", "Bearer " + ctx.bearer())
             .header("traceparent", "00-" + ctx.traceId() + "-" + spanId + "-01");
        }
        return b.build();
    }

    /** Which context does the code at this point see? */
    static Ctx ctx(Ctx captured) { return mode.equals("explicit") ? captured : CURRENT.get(); }

    /** Did the server receive the full context? */
    static boolean forwarded(String body, Ctx expected) {
        return body.contains("rid=" + expected.requestId() + "|")
            && body.contains("tenant=" + expected.tenant() + "|")
            && body.contains("auth=Bearer " + expected.bearer() + "|")
            && body.contains("tp=00-" + expected.traceId() + "-");
    }

    static String send(HttpRequest r) {
        try { return CLIENT.send(r, HttpResponse.BodyHandlers.ofString()).body(); }
        catch (Exception e) { throw new CompletionException(e); }
    }

    /** A legacy wrapper that synchronizes around the blocking call (old SDKs, drivers, caches do this). */
    static final class LegacyClient {
        synchronized String fetch(HttpRequest r) { return send(r); }
    }

    /** One run: returns the number of the 2N calls whose context arrived intact. */
    static int run(String method, int n, Ctx inbound) throws Exception {
        CURRENT.set(inbound);                       // the "request thread" has the context
        Ctx captured = inbound;                     // explicit mode captures it here
        AtomicInteger ok = new AtomicInteger();
        try {
            switch (method) {
                case "loop" -> {
                    for (int i = 0; i < n; i++) {
                        String a = send(get(ctx(captured), i, ""));
                        String b = send(get(ctx(captured), i, "/price"));
                        if (forwarded(a, inbound)) ok.incrementAndGet();
                        if (forwarded(b, inbound)) ok.incrementAndGet();
                    }
                }
                case "cf-async" -> {                // non-blocking HttpClient; second call built in a callback
                    List<CompletableFuture<Void>> all = new ArrayList<>(n);
                    for (int i = 0; i < n; i++) {
                        final int k = i;
                        all.add(CLIENT.sendAsync(get(ctx(captured), k, ""), HttpResponse.BodyHandlers.ofString())
                            .thenCompose(r1 -> {
                                if (forwarded(r1.body(), inbound)) ok.incrementAndGet();
                                return CLIENT.sendAsync(get(ctx(captured), k, "/price"), HttpResponse.BodyHandlers.ofString());
                            })
                            .thenAccept(r2 -> { if (forwarded(r2.body(), inbound)) ok.incrementAndGet(); }));
                    }
                    CompletableFuture.allOf(all.toArray(CompletableFuture[]::new)).join();
                }
                case "cf-pool", "cf-common" -> {    // supplyAsync wrapping blocking calls
                    ExecutorService pool = method.equals("cf-pool") ? Executors.newFixedThreadPool(64) : null;
                    try {
                        List<CompletableFuture<Void>> all = new ArrayList<>(n);
                        for (int i = 0; i < n; i++) {
                            final int k = i;
                            Runnable task = () -> {
                                if (forwarded(send(get(ctx(captured), k, "")), inbound)) ok.incrementAndGet();
                                if (forwarded(send(get(ctx(captured), k, "/price")), inbound)) ok.incrementAndGet();
                            };
                            all.add(pool == null ? CompletableFuture.runAsync(task) : CompletableFuture.runAsync(task, pool));
                        }
                        CompletableFuture.allOf(all.toArray(CompletableFuture[]::new)).join();
                    } finally { if (pool != null) pool.shutdown(); }
                }
                case "vt", "vt-vtclient", "vt-sync" -> {           // one virtual thread per task, plain blocking code
                    try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
                        for (int i = 0; i < n; i++) {
                            final int k = i;
                            exec.submit(() -> {
                                LegacyClient legacy = method.equals("vt-sync") ? new LegacyClient() : null;
                                String a = legacy == null ? send(get(ctx(captured), k, "")) : legacy.fetch(get(ctx(captured), k, ""));
                                String b = legacy == null ? send(get(ctx(captured), k, "/price")) : legacy.fetch(get(ctx(captured), k, "/price"));
                                if (forwarded(a, inbound)) ok.incrementAndGet();
                                if (forwarded(b, inbound)) ok.incrementAndGet();
                                return null;
                            });
                        }
                    }
                }
                default -> throw new IllegalArgumentException(method);
            }
        } finally { CURRENT.remove(); }
        return ok.get();
    }

    public static void main(String[] args) throws Exception {
        base = "http://127.0.0.1:" + args[0];
        String method = args[1]; int n = Integer.parseInt(args[2]); mode = args[3]; int runs = Integer.parseInt(args[4]);
        var builder = HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1).connectTimeout(Duration.ofSeconds(10));
        if (method.equals("vt-vtclient")) builder.executor(Executors.newVirtualThreadPerTaskExecutor());
        CLIENT = builder.build();
        Ctx inbound = new Ctx("req-7f3a", "acme", "tok-" + UUID.nameUUIDFromBytes(new byte[]{1}), "4bf92f3577b34da6a3ce929d0e0e4736");
        ThreadMXBean mx = ManagementFactory.getThreadMXBean();

        run(method, Math.min(n, 50), inbound);       // warm-up: JIT, connection pool
        List<Long> times = new ArrayList<>(); int okLast = 0;
        mx.resetPeakThreadCount();
        for (int r = 0; r < runs; r++) {
            long t0 = System.nanoTime();
            okLast = run(method, n, inbound);
            times.add((System.nanoTime() - t0) / 1_000_000);
        }
        List<Long> sorted = new ArrayList<>(times); Collections.sort(sorted);
        System.out.printf("{\"jdk\":%d,\"method\":\"%s\",\"n\":%d,\"calls\":%d,\"mode\":\"%s\",\"runsMs\":%s,\"medianMs\":%d,"
                + "\"forwarded\":%d,\"peakPlatformThreads\":%d,\"cores\":%d}%n",
            Runtime.version().feature(), method, n, 2 * n, mode, times, sorted.get(sorted.size() / 2),
            okLast, mx.getPeakThreadCount(), Runtime.getRuntime().availableProcessors());
    }
}

// GET benchmark, ScopedValue + StructuredTaskScope variant (JDK 25+; StructuredTaskScope is PREVIEW).
// Same workload and checks as GetBench. Compile per JDK with --release <N> --enable-preview.
//
// Usage: java --enable-preview GetBenchScoped <port> <method> <n> <runs>
//   method: sts        - ScopedValue bound once, subtasks forked in a StructuredTaskScope (inherit it)
//           vt-scoped  - ScopedValue bound once, subtasks on a plain virtual-thread executor (do NOT inherit it)
import java.lang.management.*;
import java.net.URI;
import java.net.http.*;
import java.time.Duration;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class GetBenchScoped {
    record Ctx(String requestId, String tenant, String bearer, String traceId) {}

    static final ScopedValue<Ctx> CURRENT = ScopedValue.newInstance();
    static final HttpClient CLIENT = HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1)
            .connectTimeout(Duration.ofSeconds(10)).build();
    static String base;

    static HttpRequest get(int i, String suffix) {
        var b = HttpRequest.newBuilder(URI.create(base + "/item/" + i + suffix)).timeout(Duration.ofSeconds(60)).GET();
        if (CURRENT.isBound()) {                       // read the context where the request is built
            Ctx ctx = CURRENT.get();
            String spanId = String.format("%016x", (long) i * 2 + (suffix.isEmpty() ? 0 : 1) + 1);
            b.header("X-Request-Id", ctx.requestId())
             .header("X-Tenant-Id", ctx.tenant())
             .header("Authorization", "Bearer " + ctx.bearer())
             .header("traceparent", "00-" + ctx.traceId() + "-" + spanId + "-01");
        }
        return b.build();
    }

    static boolean forwarded(String body, Ctx expected) {
        return body.contains("rid=" + expected.requestId() + "|")
            && body.contains("tenant=" + expected.tenant() + "|")
            && body.contains("auth=Bearer " + expected.bearer() + "|")
            && body.contains("tp=00-" + expected.traceId() + "-");
    }

    static String send(HttpRequest r) throws Exception {
        return CLIENT.send(r, HttpResponse.BodyHandlers.ofString()).body();
    }

    static int task(int k, Ctx expected) throws Exception {
        int ok = 0;
        if (forwarded(send(get(k, "")), expected)) ok++;
        if (forwarded(send(get(k, "/price")), expected)) ok++;
        return ok;
    }

    static int run(String method, int n, Ctx inbound) throws Exception {
        return ScopedValue.where(CURRENT, inbound).call(() -> {
            AtomicInteger ok = new AtomicInteger();
            if (method.equals("sts")) {
                try (var scope = StructuredTaskScope.open()) {      // forks inherit CURRENT automatically
                    for (int i = 0; i < n; i++) { final int k = i; scope.fork(() -> ok.addAndGet(task(k, inbound))); }
                    scope.join();                                    // throws if any subtask failed
                }
            } else {
                try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {  // executor threads see nothing
                    for (int i = 0; i < n; i++) { final int k = i; exec.submit(() -> ok.addAndGet(task(k, inbound))); }
                }
            }
            return ok.get();
        });
    }

    public static void main(String[] args) throws Exception {
        base = "http://127.0.0.1:" + args[0];
        String method = args[1]; int n = Integer.parseInt(args[2]); int runs = Integer.parseInt(args[3]);
        Ctx inbound = new Ctx("req-7f3a", "acme", "tok-" + UUID.nameUUIDFromBytes(new byte[]{1}), "4bf92f3577b34da6a3ce929d0e0e4736");
        ThreadMXBean mx = ManagementFactory.getThreadMXBean();
        run(method, Math.min(n, 50), inbound);
        List<Long> times = new ArrayList<>(); int okLast = 0;
        mx.resetPeakThreadCount();
        for (int r = 0; r < runs; r++) {
            long t0 = System.nanoTime();
            okLast = run(method, n, inbound);
            times.add((System.nanoTime() - t0) / 1_000_000);
        }
        List<Long> sorted = new ArrayList<>(times); Collections.sort(sorted);
        System.out.printf("{\"jdk\":%d,\"method\":\"%s\",\"n\":%d,\"calls\":%d,\"mode\":\"scoped\",\"runsMs\":%s,\"medianMs\":%d,"
                + "\"forwarded\":%d,\"peakPlatformThreads\":%d,\"cores\":%d}%n",
            Runtime.version().feature(), method, n, 2 * n, times, sorted.get(sorted.size() / 2),
            okLast, mx.getPeakThreadCount(), Runtime.getRuntime().availableProcessors());
    }
}

What the numbers say

  1. Any concurrency beats the loop by about 100×. The for loop made 400 calls in 12.5 s on the Windows desktop and 8.6 s in the cloud. Every concurrent method that didn't pin finished the same 400 calls in 88–343 ms, on either machine and any JDK. MEASURED
  2. Among concurrent methods, the differences are small as long as nothing pins and nothing is pool-limited. At 1,000 tasks on the Windows desktop (JDK 26): sendAsync 403 ms, virtual threads 439 ms, VT with a VT-backed client 370 ms, structured scope 397 ms. The case for virtual threads is that the code stays a plain loop of blocking calls, not that they're faster than a well-written async chain. MEASURED
  3. A fixed pool is a speed limit, and Little's law predicts it. 1,000 tasks in waves of 64 is 16 waves. On the Windows desktop, each 2-call task took about 62 ms (see 5), so 16 × 62 ≈ 990 ms; the measured times were 994 ms and 997 ms. MEASURED
  4. Pinning is the version difference that matters. With the synchronized wrapper, JDK 21 took 3.9 s for 1,000 tasks on the 16-thread Windows desktop and 20.8 s on 2 vCPUs. JDK 26 took 437 ms, and JDK 25 and 27 in the cloud took 465 ms and 510 ms. On 21, throughput falls to one call per carrier, so the damage grows as the core count shrinks. MEASURED
  5. The Windows timer showed up in the loop. Each sequential call took about 31.2 ms on Windows versus 21.5 ms on Linux for a 20 ms sleep. That fits Windows' default 15.6 ms timer tick: two ticks is 31.25 ms. It shifts the absolute desktop numbers, not the comparisons. INFERRED
  6. Blocking on the common pool can fail outright. runAsync without an executor at 1,000 tasks threw RejectedExecutionException: Thread limit exceeded replacing blocked worker on JDK 21 and 26 on the Windows desktop, and on 25 and 27 in the cloud. Only cloud JDK 21 survived, by growing to 591 platform threads. The common pool adds threads to make up for blocked workers, but only up to a limit. Never put blocking calls on it. MEASURED
  7. HttpClient brings its own platform threads. Even when you call the blocking send() from virtual threads, the default client hands work to an internal cached thread pool: 182 peak platform threads on the Windows desktop. Giving the client a virtual-thread executor cut that to 24 at no cost in time. MEASURED
  8. Other differences between JDK versions weren't consistent. For example, sendAsync at 1,000 tasks was faster on 25 than 21 in the cloud (594 ms vs 1,319 ms) but slower on 26 than 21 on the Windows desktop (403 ms vs 328 ms). Treat gaps under 2× as noise unless they repeat on your hardware. MEASURED

13. At work: Spring executor beans, RestTemplate → RestClient, Java 17 → 25

This section follows a migration path common in enterprise Spring codebases: Spring executors defined as beans, headers forwarded on every outbound call, most code on RestTemplate and Java 17 today, and RestClient on Java 25 as the target. The benchmark is a real Spring Boot app. A request comes in with the four headers, the controller fans out to the same echo server as section 12, and every response is checked. It ran on three stacks: Java 17 + Boot 3.5 (today), Java 25 + Boot 3.5 (JDK upgrade only) and Java 25 + Boot 4.1 (the target). Each stack ran on two machines: the Windows desktop (i7-1260P, 16 threads, Windows 11; Temurin 17.0.20.1 and 25.0.5) and the 2-vCPU Linux cloud machine (Temurin 17.0.21 and 25.0.5). MEASURED

Where Spring stands. The Spring Framework 7.0 reference marks RestTemplate as deprecated in favor of RestClient. The @Deprecated annotation lands in 7.1, and removal is planned for 8.0. Spring Boot 4.2 milestones deprecate RestTemplateBuilder. RestClient has existed since Spring Framework 6.1 (Boot 3.2), so your Java 17 repos can start using it now. SOURCED

How the headers travel

Three pieces, the same on Java 17 and 25, and the same for RestTemplate and RestClient (both accept a ClientHttpRequestInterceptor):

  1. A filter captures the headers once into an immutable value, kept in a ThreadLocal for the request thread. Copying the values, rather than holding on to HttpServletRequest, means a worker can never read a request object Tomcat has already recycled.
  2. A TaskDecorator on every executor bean copies that value onto the worker thread, and always restores it in finally.
  3. An interceptor on every client adds the headers to each outbound call.
// 1. capture: OncePerRequestFilter
ForwardedHeaders.set(ForwardedHeaders.from(request));       // X-Request-Id, X-Tenant-Id, Authorization, traceparent
try { chain.doFilter(request, response); } finally { ForwardedHeaders.set(null); }

// 2. propagate: one TaskDecorator bean, set on every executor
@Bean TaskDecorator forwardedHeadersDecorator() {
    return task -> {
        ForwardedHeaders captured = ForwardedHeaders.current();   // on the submitting thread
        return () -> {
            ForwardedHeaders previous = ForwardedHeaders.current();
            ForwardedHeaders.set(captured);
            try { task.run(); } finally { ForwardedHeaders.set(previous); }
        };
    };
}

// 3. send: one interceptor, used by RestTemplate and RestClient
@Bean ClientHttpRequestInterceptor forwardHeadersInterceptor() {
    return (req, body, exec) -> {
        ForwardedHeaders h = ForwardedHeaders.current();
        if (h != null) h.applyTo(req.getHeaders());
        return exec.execute(req, body);
    };
}

If you also need MDC or tracing context on the worker, copy it in the same decorator, or use Spring's ContextPropagatingTaskDecorator (present in spring-core 6.2.19, which we checked in the jar; it needs Micrometer's context-propagation library). The alternative to all three pieces is to pass the value explicitly: restClient.get().uri(…).headers(captured::applyTo). The benchmark measures both.

What this means for your migration

Numbers are from the Windows desktop unless marked. There a 20 ms wait costs about 31 ms per call (the Windows timer, §12), so each 2-call task takes about 62 ms.

  1. On Java 17, the pool size is your throughput. A pool shaped like Boot's default (8 threads) took 7.8 s for 1,000 tasks. The 64-thread pool took 994 ms. Little's law predicts both almost exactly: 1,000 ÷ 8 × 62 ms ≈ 7.75 s, and 1,000 ÷ 64 → 16 waves × 62 ms ≈ 0.99 s. MEASURED
  2. The JDK upgrade alone changes nothing. Same Boot 3.5 jar, same 64-thread pool: 994 ms on Java 17, 995 ms on Java 25. MEASURED
  3. Swapping the executor bean is where Java 25 pays off. The virtual-thread bean with a limit of 200 took 311 ms for 1,000 tasks versus 996 ms on the pool, and 62 ms versus 247 ms for 200. The limit costs something: 1,000 ÷ 200 = 5 waves. Without it, the cloud machine finished 1,000 in 133 ms, but the Windows desktop refused connections (see connection storms). Set the limit to what your downstream can actually take. MEASURED
  4. RestTemplate → RestClient is not a performance change. With the same factory and executor: 63 ms vs 66 ms on the Windows desktop, and 133 ms vs 133 ms in the cloud. Migrate for the API and the deprecation, and keep the request factory under control while you do. MEASURED
  5. Boot 3.5 → 4.1 made no measurable difference on Java 25: 311 ms vs 311 ms. MEASURED
  6. The request factory is the trap. HttpClient 5's default pool took over 12 s on the Windows desktop (8 s in the cloud) on every stack, including Java 17 with 64 threads. That's 5 connections per host no matter how many threads you have. With the pool sized, HttpClient 5, HttpURLConnection and java.net.http were within about 15% of each other on the Windows desktop. MEASURED
  7. Virtual threads don't carry your headers. Without the decorator, both the platform pool and the virtual-thread executor forwarded 0 of 100 calls, on both machines and every stack. With it, or with explicit headers, every call that completed had all four. MEASURED
  8. Unbounded virtual-thread fan-out can fail on a cold pool. On the Windows desktop, 1,000 tasks with no limit were refused at connect time on every Java 25 stack. With the limit of 200, every run succeeded. MEASURED
  9. Stale pooled connections show up too. With several HttpClient 5 pools each holding hundreds of keep-alive connections, our test server started closing idle ones. HttpClient 5 then reused dead connections and threw NoHttpResponseException. Set an idle-eviction or validate-after-inactivity policy when you size a pool up. MEASURED INFERRED

A migration order that keeps each step measurable

  1. Now, on Java 17: add the filter, TaskDecorator and interceptor. Put the decorator on every executor bean. Replace any use of the 8-thread default executor for fan-out. Size the HttpClient 5 pool to at least the executor's thread count.
  2. Start new code on RestClient (available on Boot 3.2+). Bridge old code with RestClient.create(restTemplate), which keeps the existing request factory and interceptors, then move to RestClient.builder() with an explicit factory. SOURCED
  3. Upgrade to Java 25 with no other change, and confirm nothing moved (finding 2).
  4. Swap the fan-out executor bean to the virtual-thread SimpleAsyncTaskExecutor with the same decorator and a concurrency limit. Protect each downstream with a Semaphore or setConcurrencyLimit, and size its connection pool to that limit (§7). Test from a cold start, not only with warm pools.
  5. Turn on spring.threads.virtual.enabled for request handling, and load-test with JFR recording jdk.VirtualThreadPinned (§10).
  6. Boot 4: add spring-boot-starter-restclient; RestTemplate auto-configuration and RestTemplateBuilder are on their way out. SOURCED

ForwardedHeaders.java

package demo;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.http.HttpHeaders;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/**
 * The inbound headers we must forward on every outbound call, captured once as an immutable value.
 * Holding values (not the HttpServletRequest) means a task can never read a recycled request object.
 */
public record ForwardedHeaders(Map<String, String> values) {

    static final List<String> NAMES = List.of("X-Request-Id", "X-Tenant-Id", "Authorization", "traceparent");

    /** Thread-bound copy, filled by {@link CaptureFilter}, copied to worker threads by the TaskDecorator. */
    private static final ThreadLocal<ForwardedHeaders> CURRENT = new ThreadLocal<>();

    static ForwardedHeaders from(HttpServletRequest request) {
        Map<String, String> m = new LinkedHashMap<>();
        for (String name : NAMES) {
            String v = request.getHeader(name);
            if (v != null) m.put(name, v);
        }
        return new ForwardedHeaders(Map.copyOf(m));
    }

    static ForwardedHeaders current() { return CURRENT.get(); }
    static void set(ForwardedHeaders h) { if (h == null) CURRENT.remove(); else CURRENT.set(h); }

    /** Write onto an outbound request. traceparent keeps the trace id; the span id would be new per call in real tracing. */
    void applyTo(HttpHeaders headers) {
        values.forEach(headers::set);
    }

    @Component
    static class CaptureFilter extends OncePerRequestFilter {
        @Override
        protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
                throws ServletException, IOException {
            set(from(req));
            try { chain.doFilter(req, res); } finally { set(null); }
        }
    }
}

package demo;

import org.apache.hc.client5.http.impl.classic.HttpClients;
import org.apache.hc.client5.http.impl.io.PoolingHttpClientConnectionManagerBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.task.SimpleAsyncTaskExecutor;
import org.springframework.core.task.TaskDecorator;
import org.springframework.http.client.ClientHttpRequestFactory;
import org.springframework.http.client.ClientHttpRequestInterceptor;
import org.springframework.http.client.HttpComponentsClientHttpRequestFactory;
import org.springframework.http.client.JdkClientHttpRequestFactory;
import org.springframework.http.client.SimpleClientHttpRequestFactory;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.RestTemplate;

import java.net.http.HttpClient;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.concurrent.Executor;

@Configuration
public class HttpConfig {

    // ---------------------------------------------------------------- context propagation

    /** Copies the caller's ForwardedHeaders onto the worker thread, and always cleans up. */
    @Bean
    TaskDecorator forwardedHeadersDecorator() {
        return task -> {
            ForwardedHeaders captured = ForwardedHeaders.current();          // runs on the submitting thread
            return () -> {
                ForwardedHeaders previous = ForwardedHeaders.current();
                ForwardedHeaders.set(captured);
                try { task.run(); } finally { ForwardedHeaders.set(previous); } // pooled threads must not keep it
            };
        };
    }

    /** Adds the thread's ForwardedHeaders to every outbound call (RestTemplate and RestClient share this type). */
    @Bean
    ClientHttpRequestInterceptor forwardHeadersInterceptor() {
        return (request, body, execution) -> {
            ForwardedHeaders h = ForwardedHeaders.current();
            if (h != null) h.applyTo(request.getHeaders());
            return execution.execute(request, body);
        };
    }

    // ---------------------------------------------------------------- executor beans

    /** Same shape as Spring Boot's default applicationTaskExecutor: 8 core threads, unbounded queue. */
    @Bean
    ThreadPoolTaskExecutor bootDefaultLikeExecutor(TaskDecorator decorator) {
        return pool("boot8-", 8, decorator);
    }

    @Bean
    ThreadPoolTaskExecutor platformExecutor(TaskDecorator decorator) {
        return pool("plat-", 64, decorator);
    }

    @Bean
    ThreadPoolTaskExecutor platformExecutorNoDecorator() {
        return pool("plat-nodec-", 64, null);
    }

    private static ThreadPoolTaskExecutor pool(String prefix, int size, TaskDecorator decorator) {
        ThreadPoolTaskExecutor e = new ThreadPoolTaskExecutor();
        e.setCorePoolSize(size);
        e.setMaxPoolSize(size);
        e.setQueueCapacity(Integer.MAX_VALUE);
        e.setThreadNamePrefix(prefix);
        if (decorator != null) e.setTaskDecorator(decorator);
        e.initialize();
        return e;
    }

    /** One virtual thread per task (Java 21+). On Java 17 this bean is a placeholder that refuses work. */
    @Bean
    Executor virtualExecutor(TaskDecorator decorator) {
        return virtual("vt-", decorator);
    }

    @Bean
    Executor virtualExecutorNoDecorator() {
        return virtual("vt-nodec-", null);
    }

    /** Virtual threads with at most 200 tasks in flight; extra submissions wait (throttle) instead of failing. */
    @Bean
    Executor virtualExecutorLimited(TaskDecorator decorator) {
        Executor e = virtual("vt-lim-", decorator);
        if (e instanceof SimpleAsyncTaskExecutor s) s.setConcurrencyLimit(200);
        return e;
    }

    private static Executor virtual(String prefix, TaskDecorator decorator) {
        if (Runtime.version().feature() < 21) {
            return task -> { throw new UnsupportedOperationException("virtual threads need Java 21+"); };
        }
        SimpleAsyncTaskExecutor e = new SimpleAsyncTaskExecutor(prefix);
        e.setVirtualThreads(true);
        if (decorator != null) e.setTaskDecorator(decorator);
        return e;
    }

    // ---------------------------------------------------------------- request factories

    /** Apache HttpClient 5 with a pool sized for the fan-out (what you should configure). */
    static ClientHttpRequestFactory hc5Tuned() {
        var cm = PoolingHttpClientConnectionManagerBuilder.create().setMaxConnTotal(1000).setMaxConnPerRoute(1000).build();
        return new HttpComponentsClientHttpRequestFactory(HttpClients.custom().setConnectionManager(cm).build());
    }

    /** Apache HttpClient 5 with Spring's no-arg constructor: HttpClient 5's default pool. */
    static ClientHttpRequestFactory hc5Default() {
        return new HttpComponentsClientHttpRequestFactory();
    }

    /** java.net.http.HttpClient (JDK 11+), no connection-pool cap. */
    static ClientHttpRequestFactory jdk() {
        return new JdkClientHttpRequestFactory(HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1).build());
    }

    /** HttpURLConnection, what `new RestTemplate()` uses. */
    static ClientHttpRequestFactory simple() {
        return new SimpleClientHttpRequestFactory();
    }

    // ---------------------------------------------------------------- clients

    @Bean
    RestTemplate restTemplate(ClientHttpRequestInterceptor forward) {
        RestTemplate rt = new RestTemplate(hc5Tuned());
        rt.getInterceptors().add(forward);
        return rt;
    }

    /** RestClients keyed by request factory, all with the same forwarding interceptor. */
    record RestClients(Map<String, RestClient> byFactory) {}

    @Bean
    RestClients restClients(ClientHttpRequestInterceptor forward) {
        Map<String, RestClient> m = new LinkedHashMap<>();
        m.put("hc5-tuned", RestClient.builder().requestFactory(hc5Tuned()).requestInterceptor(forward).build());
        m.put("hc5-default", RestClient.builder().requestFactory(hc5Default()).requestInterceptor(forward).build());
        m.put("jdk", RestClient.builder().requestFactory(jdk()).requestInterceptor(forward).build());
        m.put("simple", RestClient.builder().requestFactory(simple()).requestInterceptor(forward).build());
        return new RestClients(m);
    }

    /** RestClient with no interceptor, for the explicit-headers pattern. */
    @Bean
    RestClient plainRestClient() {
        return RestClient.builder().requestFactory(hc5Tuned()).build();
    }
}

/**

 * Each of n tasks calls GET /item/{i} then GET /item/{i}/price on the downstream echo server.

@RestController
public class FanoutController {

    public FanoutController(RestTemplate restTemplate, HttpConfig.RestClients restClients,

                            @Qualifier("bootDefaultLikeExecutor") Executor boot8,
                            @Qualifier("platformExecutor") Executor platform,
                            @Qualifier("platformExecutorNoDecorator") Executor platformNoDec,
                            @Qualifier("virtualExecutor") Executor virtual,
                            @Qualifier("virtualExecutorNoDecorator") Executor virtualNoDec,
                            @Qualifier("virtualExecutorLimited") Executor virtualLimited,
                            @Value("${downstream.url}") String downstream) {
        this.restTemplate = restTemplate;
        this.restClients = restClients.byFactory();
        this.plainRestClient = plainRestClient;
        this.executors = Map.of("boot8", boot8, "pool", platform, "pool-nodec", platformNoDec,
                                "vt", virtual, "vt-nodec", virtualNoDec, "vt-limit", virtualLimited);
        this.downstream = downstream;
    }

    @GetMapping("/fanout")
    public Map<String, Object> fanout(@RequestParam String scenario, @RequestParam int n,
                                      @RequestParam(defaultValue = "hc5-tuned") String factory,
                                      HttpServletRequest inbound) {
        ForwardedHeaders expected = ForwardedHeaders.from(inbound);
        Map<String, Object> out = new LinkedHashMap<>();
        out.put("scenario", scenario); out.put("n", n); out.put("calls", 2 * n); out.put("factory", factory);
        out.put("jdk", Runtime.version().feature());
        out.put("boot", SpringBootVersion.getVersion()); out.put("framework", SpringVersion.getVersion());
        long t0 = System.nanoTime();
        try {
            int ok = run(scenario, n, factory, expected);
            out.put("ms", (System.nanoTime() - t0) / 1_000_000);
            out.put("forwarded", ok);
        } catch (Exception e) {
            Throwable root = e; while (root.getCause() != null) root = root.getCause();
            out.put("error", root.getClass().getSimpleName() + ": " + root.getMessage());
        }
        return out;
    }

    private int run(String scenario, int n, String factory, ForwardedHeaders expected) {
        AtomicInteger ok = new AtomicInteger();
        Function<String, String> call;          // path -> response body
        String executorKey;
        switch (scenario) {
            case "rt-loop" -> { call = p -> restTemplate.getForObject(downstream + p, String.class); executorKey = null; }
            case "rt-boot8" -> { call = p -> restTemplate.getForObject(downstream + p, String.class); executorKey = "boot8"; }
            case "rt-pool" -> { call = p -> restTemplate.getForObject(downstream + p, String.class); executorKey = "pool"; }
            case "rt-pool-nodec" -> { call = p -> restTemplate.getForObject(downstream + p, String.class); executorKey = "pool-nodec"; }
            case "rt-vt" -> { call = p -> restTemplate.getForObject(downstream + p, String.class); executorKey = "vt"; }
            case "rc-pool" -> { RestClient c = client(factory); call = p -> c.get().uri(downstream + p).retrieve().body(String.class); executorKey = "pool"; }
            case "rc-vt" -> { RestClient c = client(factory); call = p -> c.get().uri(downstream + p).retrieve().body(String.class); executorKey = "vt"; }
            case "rc-vt-limit" -> { RestClient c = client(factory); call = p -> c.get().uri(downstream + p).retrieve().body(String.class); executorKey = "vt-limit"; }
            case "rc-vt-nodec" -> { RestClient c = client(factory); call = p -> c.get().uri(downstream + p).retrieve().body(String.class); executorKey = "vt-nodec"; }
            case "rc-vt-explicit" -> {
                ForwardedHeaders captured = ForwardedHeaders.current();      // capture on the request thread
                call = p -> plainRestClient.get().uri(downstream + p)
                        .headers(captured::applyTo)                         // pass the value, no ThreadLocal
                        .retrieve().body(String.class);
                executorKey = "vt-nodec";
            }
            default -> throw new IllegalArgumentException("unknown scenario " + scenario);
        }
        if (executorKey == null) {
            for (int i = 0; i < n; i++) ok.addAndGet(task(call, i, expected));
            return ok.get();
        }
        Executor executor = executors.get(executorKey);
        List<CompletableFuture<Void>> all = new ArrayList<>(n);
        for (int i = 0; i < n; i++) {
            final int k = i;
            all.add(CompletableFuture.runAsync(() -> ok.addAndGet(task(call, k, expected)), executor));
        }
        CompletableFuture.allOf(all.toArray(CompletableFuture[]::new)).join();
        return ok.get();
    }

    private RestClient client(String factory) {
        RestClient c = restClients.get(factory);
        if (c == null) throw new IllegalArgumentException("unknown factory " + factory);
        return c;
    }

    /** One task: two dependent GETs. Returns how many of the two arrived with all headers. */
    private static int task(Function<String, String> call, int i, ForwardedHeaders expected) {
        int ok = 0;
        if (forwarded(call.apply("/item/" + i), expected)) ok++;
        if (forwarded(call.apply("/item/" + i + "/price"), expected)) ok++;
        return ok;
    }

    static boolean forwarded(String body, ForwardedHeaders expected) {
        Map<String, String> v = expected.values();
        return body != null
            && body.contains("rid=" + v.get("X-Request-Id") + "|")
            && body.contains("tenant=" + v.get("X-Tenant-Id") + "|")
            && body.contains("auth=" + v.get("Authorization") + "|")
            && body.contains("tp=" + v.get("traceparent") + "|");
    }
}

Exercises with answers

Exercise 1 · Predict, then run

Change Lab 2's pool to 1,000 threads. What time do you predict? Then try 10 tasks instead of 10,000. Which executor wins now?
Answer and rubric10,000 × 0.1 s ÷ 1,000 = 1 s floor. With 10 tasks both finish in about 100 ms: virtual threads only help when concurrency exceeds what the pool can hold. Full marks for using Little's law before running.

Exercise 2 · Fix a lying benchmark

Remove the warm-up loop from Lab 3 and swap the order of the two runs. What happens, and why?
Answer and rubricWhichever executor runs first looks slower, because it pays for JIT compilation of burn. Without warm-up our first version reported virtual threads as 2.3× faster on CPU work, which is false. Full marks for naming JIT warm-up and proposing warm-up rounds, repeated rounds or JMH.

Exercise 3 · Simulator: break JDK 21

In the simulator, use 2 carriers, 8 tasks, 10 ms CPU, 200 ms wait inside synchronized. Compare JDK 21–23 with 24+. Then find the smallest carrier count that makes JDK 21 match 24+.
Answer and rubric880 ms on JDK 21–23 versus 250 ms on 24+. JDK 21 needs one carrier per task (8) to match, which is exactly "back to one OS thread per task". Full marks for connecting that to why pinning made 21 rollouts risky.

Exercise 4 · Simulator: native calls

Set the wait to happen inside a native call. Does the JDK version matter? What would you do in a real service?
Answer and rubricNo; native frames pin on every JDK. Options: keep that work on a bounded platform pool, use a non-blocking API, or accept it if calls are short and rare. Full marks for proposing to measure with JFR first.

Exercise 5 · Convert a limiter

A service uses Executors.newFixedThreadPool(10) to stop itself from overloading a partner API. Rewrite it for virtual threads.
Answer and rubricnewVirtualThreadPerTaskExecutor() plus a Semaphore(10) acquired around the partner call only, as in Lab 6. Full marks for keeping the limit around the call rather than around the whole task, and for releasing it in finally.

Exercise 6 · Forward the headers

Take the CompletableFuture + sendAsync version that reads a ThreadLocal context, and make it forward all four headers on both calls. Then predict how long the 64-thread-pool version takes for 1,000 tasks at 31 ms per call, and compare with the desktop table.
Answer and rubricRead the context into a local variable before the loop and use that variable in both the first request and the one built inside thenCompose. Then 2,000 of 2,000 calls are forwarded, not 1,000. Pool: 1,000 ÷ 64 → 16 waves × 2 calls × 31 ms ≈ 990 ms, against about 994 ms measured. Full marks for explaining why the callback lost the context: it runs on a different thread.

Code review checklist

  • Is the work I/O-bound? If it's CPU-bound, virtual threads won't help.
  • Any pool of virtual threads (newFixedThreadPool with a virtual factory)? Replace it with per-task threads plus a semaphore.
  • On JDK 21–23: blocking calls inside synchronized on a hot path?
  • Native or FFM calls that block? These pin on every JDK.
  • ThreadLocal used as a cache or holding large objects?
  • Are limits expressed at the scarce resource (connections, rate limits)?
  • Preview APIs (StructuredTaskScope) in production code?
  • Does the load test record JFR and check jdk.VirtualThreadPinned?

16. Check yourself

Eight questions. Choose an answer for instant feedback, or open "Answer" if scripts are off.

1. A service's handlers spend 95% of their time waiting on a database. What do virtual threads most likely improve?

AnswerThroughput when many requests are in flight. They raise the number of requests that can wait at once. Each request still takes as long as its database call (Lab 2).

2. On JDK 25, a virtual thread calls Thread.sleep inside a synchronized block. What happens to its carrier?

AnswerIt's released; the virtual thread unmounts. JEP 491 (JDK 24) lets virtual threads unmount while holding a monitor (Lab 4).

3. Which still pins a virtual thread on JDK 25?

AnswerBlocking inside a native (JNI/FFM) frame. Native frames can't be moved to the heap, so they pin on every JDK.

4. You must not exceed 20 concurrent calls to a partner API. Best approach with virtual threads?

AnswernewVirtualThreadPerTaskExecutor() plus a Semaphore(20) around the call. Limit the resource, not the threads. The parallelism setting changes carriers and doesn't bound concurrent calls (Lab 6).

5. A CPU-bound image resize job runs 8 tasks on a 4-core box. Compared to a 4-thread pool, virtual threads will be…

AnswerAbout the same. Same cores, same work (Lab 3). They're not time-sliced, so there's no magic.

6. How many carrier threads does the default scheduler use?

AnswerAbout one per available core. Parallelism defaults to the number of available processors. 256 is the default maximum pool size, used only to compensate for some blocking.

7. Which tool should you use to find pinning on JDK 24+?

AnswerJFR's jdk.VirtualThreadPinned event. The trace flag was removed in 24, and on 21 it changed the timing we measured. JFR is the supported signal (Lab 10).

8. Which of these can you use in production on JDK 25 without preview flags?

AnswerScopedValue. ScopedValue is final in 25 (JEP 506). StructuredTaskScope is still preview, and its API changed again in 27 (Labs 7 and 8).

Glossary

CarrierThe platform thread a virtual thread is currently mounted on. From a ForkJoinPool sized to cores by default.
Mount / unmountCopying a virtual thread's stack frames onto a carrier, and saving them back to the heap when it blocks.
PinningBlocking while unable to unmount, so the carrier is held. Native frames on every JDK; also synchronized on 21–23.
ContinuationThe JDK-internal object holding a virtual thread's suspended stack.
Little's lawRequests in flight = arrival rate × time in system.
ScopedValueAn immutable value bound for the duration of a block and visible to code it calls. Final in JDK 25.
StructuredTaskScopePreview API that ties forked subtasks to a block, with cancellation on failure.
Platform threadA Thread backed one-to-one by an OS thread. What every Java thread was before JDK 21.
