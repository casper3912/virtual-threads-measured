Questions people ask

Questions reviewers and readers raised that the sections above don't answer directly. Each answer is tagged with what it rests on.

Does a normal Spring app with JDBC and HikariCP still pin on Java 25?

Mostly no. Since JDK 24 (JEP 491), synchronized and Object.wait() no longer pin, and that covers the locking inside most JDBC drivers and pools. What's left is native code (§6). SOURCED

What does change is where requests wait. HikariCP holds 10 connections by default, and a request that can't get one blocks in getConnection() for up to connectionTimeout (30 s by default), then fails. With a 64-thread pool, the pool was the queue in front of the database. With a virtual thread per request, the queue moves into Hikari. Size the Hikari pool from what the database can take, not from a thread count, and watch its pending count. It's the same backpressure lesson as the connection storm in §14. SOURCED INFERRED

Which executor do @Async methods use once I define my own Executor beans?

In Spring Boot 3.5, defining any custom Executor bean makes the auto-configured one back off, and your bean runs @EnableAsync work. Spring MVC still looks for a bean named applicationTaskExecutor. spring.threads.virtual.enabled=true switches the executors Boot builds for you, and Tomcat's request threads, to virtual threads. It doesn't change beans you built yourself. With more than one executor, name the one you mean: @Async("fanoutExecutor"). SOURCED

What do I monitor instead of thread-pool saturation?

"Active threads" stops meaning anything when every task gets its own thread. Watch the places where requests now wait:

  • permits in use and wait time at each semaphore or concurrency limit (§7);
  • Hikari's pending connections and acquire time (hikaricp.connections.pending and hikaricp.connections.acquire in Micrometer);
  • the HTTP client pool's leased and pending connections;
  • request latency percentiles.

Keep JFR's jdk.VirtualThreadPinned on in load tests (§10). SOURCED INFERRED

How much memory does a virtual thread take?

About 1 KB of heap while blocked with a shallow stack, and a few KB with a deeper one. Its stack lives on the heap and grows with the call depth. A platform thread instead reserves a native stack, 1 MB by default on 64-bit Linux (-Xss). MEASURED SOURCED

Does a contended synchronized block pin on Java 25?

No. Since JEP 491 a virtual thread waiting to enter a monitor unmounts like any other blocked thread. But contention still serializes: if every request goes through one lock, one call runs at a time, however many threads you have. Pinning wastes a carrier; contention caps throughput at the lock. Lab 4 and the GET benchmark give each task its own lock, so they show pinning, not contention (§12). SOURCED INFERRED

Should we replace ThreadLocal with ScopedValue?

Only for values used inside one request's call tree. A ScopedValue is visible to code called from the binding and to StructuredTaskScope forks. It reached 0 of 200 calls through an executor (§8, §12), and an executor is how Spring's executor beans hand work off. For forwarded headers, keep the capture-and-decorate pattern from §14. MEASURED

How much work is the 17 → 25 upgrade itself?

Treat it as a compatibility job, separate from virtual threads. On the JDK side, check for these:

  • The Security Manager is permanently disabled (JEP 486, JDK 24).
  • JDK 24 warns when code uses sun.misc.Unsafe memory access (JEP 498) or JNI (JEP 472).
  • JDK 21 warns when an agent is loaded at run time (JEP 451), which Mockito's inline mocks do.

SOURCED

On the build side, the compiler plugin, Lombok, Mockito/ByteBuddy, JaCoCo and other bytecode tools need releases that read Java 25 class files. In our runs the same jar with the same pool took the same time on 17 and 25 (§14). So ship the JDK change on its own, and measure before changing executors. MEASURED INFERRED
