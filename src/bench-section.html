12. GET requests: for loop vs CompletableFuture vs virtual threads

This is the comparison most teams actually need: a handler has to make a batch of outbound GET calls and forward the caller's identity on every one. The benchmark runs the same job eight ways, on three JDKs in the cloud and two JDKs on the Windows desktop, and checks every response to confirm the headers arrived. MEASURED

The workload

  • N tasks (200 or 1,000). Each task calls GET /item/{i}, then a dependent GET /item/{i}/price, so a run makes 2N calls.
  • A local echo server in its own JVM waits 20 ms per request, standing in for a real backend. It sends back the headers it received.
  • Context forwarded on every call: X-Request-Id, X-Tenant-Id, Authorization: Bearer … and a W3C traceparent (same trace ID, new span ID per call). A call counts as forwarded only if the server echoed all four.
  • Timing: one warm-up run, then the median of three runs. Peak platform threads come from ThreadMXBean, which doesn't count virtual threads.
  • Same bytecode on every JDK: the core benchmark is compiled once with --release 21. The ScopedValue variant is compiled per JDK because StructuredTaskScope is still preview.

With perfect concurrency a task takes about 2 × 20 = 40 ms, so the best possible time for any N is roughly 40 ms plus overhead. In practice the floor is set by how fast the machine can push 400 or 2,000 HTTP exchanges through one client and one server.

The eight methods, and how each forwards the context

Every method builds its requests with the same helper. The only question is which Ctx it has in hand when it builds one:

record Ctx(String requestId, String tenant, String bearer, String traceId) {}

static HttpRequest get(Ctx ctx, int i, String suffix) {
    var b = HttpRequest.newBuilder(URI.create(base + "/item/" + i + suffix)).GET();
    if (ctx != null) {
        b.header("X-Request-Id", ctx.requestId())
         .header("X-Tenant-Id", ctx.tenant())
         .header("Authorization", "Bearer " + ctx.bearer())
         .header("traceparent", "00-" + ctx.traceId() + "-" + newSpanId() + "-01");
    }
    return b.build();
}

What the numbers say

  1. Any concurrency beats the loop by about 100×. The for loop made 400 calls in {{B:desktop:21:loop:200}} on the Windows desktop and {{B:container:21:loop:200}} in the cloud. Every concurrent method that didn't pin finished the same 400 calls in 88–343 ms, on either machine and any JDK. MEASURED
  2. Among concurrent methods, the differences are small as long as nothing pins and nothing is pool-limited. At 1,000 tasks on the Windows desktop (JDK 26): sendAsync {{B:desktop:26:cf-async:1000}}, virtual threads {{B:desktop:26:vt:1000}}, VT with a VT-backed client {{B:desktop:26:vt-vtclient:1000}}, structured scope {{B:desktop:26:sts:1000}}. The case for virtual threads is that the code stays a plain loop of blocking calls, not that they're faster than a well-written async chain. MEASURED
  3. A fixed pool is a speed limit, and Little's law predicts it. 1,000 tasks in waves of 64 is 16 waves. On the Windows desktop, each 2-call task took about 62 ms (see 5), so 16 × 62 ≈ 990 ms; the measured times were {{B:desktop:21:cf-pool:1000}} and {{B:desktop:26:cf-pool:1000}}. MEASURED
  4. Pinning is the version difference that matters. With the synchronized wrapper, JDK 21 took {{B:desktop:21:vt-sync:1000}} for 1,000 tasks on the 16-thread Windows desktop and {{B:container:21:vt-sync:1000}} on 2 vCPUs. JDK 26 took {{B:desktop:26:vt-sync:1000}}, and JDK 25 and 27 in the cloud took {{B:container:25:vt-sync:1000}} and {{B:container:27:vt-sync:1000}}. On 21, throughput falls to one call per carrier, so the damage grows as the core count shrinks. MEASURED
  5. The Windows timer showed up in the loop. Each sequential call took about {{PER_CALL:desktop}} ms on Windows versus {{PER_CALL:container}} ms on Linux for a 20 ms sleep. That fits Windows' default 15.6 ms timer tick: two ticks is 31.25 ms. It shifts the absolute desktop numbers, not the comparisons. INFERRED
  6. Blocking on the common pool can fail outright. runAsync without an executor at 1,000 tasks threw RejectedExecutionException: Thread limit exceeded replacing blocked worker on JDK 21 and 26 on the Windows desktop, and on 25 and 27 in the cloud. Only cloud JDK 21 survived, by growing to {{BT:container:21:cf-common:1000}} platform threads. The common pool adds threads to make up for blocked workers, but only up to a limit. Never put blocking calls on it. MEASURED
  7. HttpClient brings its own platform threads. Even when you call the blocking send() from virtual threads, the default client hands work to an internal cached thread pool: {{BT:desktop:26:vt:1000}} peak platform threads on the Windows desktop. Giving the client a virtual-thread executor cut that to {{BT:desktop:26:vt-vtclient:1000}} at no cost in time. MEASURED
  8. Other differences between JDK versions weren't consistent. For example, sendAsync at 1,000 tasks was faster on 25 than 21 in the cloud ({{B:container:25:cf-async:1000}} vs {{B:container:21:cf-async:1000}}) but slower on 26 than 21 on the Windows desktop ({{B:desktop:26:cf-async:1000}} vs {{B:desktop:21:cf-async:1000}}). Treat gaps under 2× as noise unless they repeat on your hardware. MEASURED

Header and context forwarding: what survives a thread hop

Performance only counts if every call carries the right identity. Most Java code keeps the current request in a ThreadLocal (Spring's RequestContextHolder, SLF4J's MDC, many security contexts). This table runs each method in the naive style: the request is built from ThreadLocal.get() wherever the code happens to be running. It also shows ScopedValue with and without a structured scope. {{CTX_TABLE}}
  • ThreadLocal context only survives where no thread changes. The loop kept it. sendAsync lost it on exactly half the calls: the first request is built on the caller's thread, but the dependent second request is built inside thenCompose on one of the client's threads. Pools, the common pool and virtual threads lost it on every call.
  • Virtual threads don't fix this by themselves. A new virtual thread starts with empty ThreadLocals, just like a pool thread.
  • ScopedValue reaches structured subtasks only. Forks of a StructuredTaskScope inherited it on every call. The same binding submitted to a plain virtual-thread executor reached none of them.
  • The pattern that works everywhere is explicit capture. All the timing results above read the context into a local variable on the request thread before fanning out. Every one of those runs forwarded all four headers on every call (the self-tests check this).
Recommended shape for a handler that fans out GETs on JDK 25+: 
Ctx ctx = Ctx.from(inboundRequest);                    // capture once, on the request thread
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    var futures = ids.stream()
        .map(id -> exec.submit(() -> send(get(ctx, id, "")))) // ctx travels as a value
        .toList();
    // collect results...
}
// with an HttpClient built once:  HttpClient.newBuilder().executor(Executors.newVirtualThreadPerTaskExecutor())
If your logging or security code reads a ThreadLocal such as MDC, restore it at the start of each task: MDC.setContextMap(captured) and clear it in finally. Or move that context to a ScopedValue and use StructuredTaskScope once it's final. INFERRED
