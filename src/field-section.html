15. What we hit, and what others have reported

Every failure in this page's benchmarks has been reported elsewhere: in OpenJDK mailing lists and bug trackers, Spring issues, library docs and production write-ups. This section links each one to those reports, so you can tell a quirk of this test setup from something your services will meet. Where our own runs confirm a cause, the tag says so.

Connection storms: the server's accept queue, confirmed

Our desktop fan-out failed with Connection refused from 500 simultaneous connections up (§13). The leading explanation is the server's listen backlog: the operating system's queue of connections that have arrived but haven't been accepted yet. When the queue is full, Windows rejects the next connect with WSAECONNREFUSED. SOURCED

OpenJDK bug JDK-8330940 says Java servers on Windows 8 and later couldn't get a backlog above 200, whatever they asked for. The fix uses Windows' SOMAXCONN_HINT to allow up to 65,535, and was integrated in June 2025 for JDK 26. Our echo server asked for 8,192 but ran on JDK 25. So we moved only the server to OpenJDK 26 and repeated the cold-start test, keeping the app on Java 25 with no concurrency limit: SOURCED MEASURED

With the server on JDK 26, every size up to 2,000 tasks (4,000 calls) succeeded. That pins the failure on the server's 200-connection queue, not on the client. The lesson for your services holds anyway. The downstream's accept queue, its load balancer and its connection limits are not yours to tune, and virtual threads are what make the burst possible. A loom-dev thread from November 2025 describes the same pattern at larger scale. A Spring Boot app making 10,000 requests on virtual threads stalled for 12–30 seconds after opening about 8,000 connections at once, while the platform-thread version kept about 140 connections open. Alan Bateman's first suspect was the backlog (net.core.somaxconn on Linux). Raising Tomcat's accept-count and max-connections also removed the stall. MongoDB documented the same effect years earlier: a spike of 5,000 new connections against the default backlog of 128 caused latencies around a minute. SOURCED

What we hitWhat others reportWhat to do
Pinning on JDK 21: synchronized around a blocking call ran 1,000 tasks in 20.8 s on 2 cores and 3.9 s on 16 threads (§6, §12).InfoQ traces a production stall class at Netflix to exactly this, and calls JDK 25 the natural LTS target because it is the first to include JEP 491. A field guide on NLJUG describes an incident where an app on virtual threads behaved like a 420-requests-per-second thread pool. InfoWorld covered Oracle's own write-up of the problem in 2024.Upgrade to 25. On 21, find pinning with JFR and move blocking calls out of synchronized on hot paths.
-Djdk.tracePinnedThreads changed the timing it was meant to diagnose (§10).Users reported on loom-dev in 2023 that the flag could hang applications. JDK-8322846 found that printing the stack trace could block waiting for System.out's lock. It was fixed in JDK 22 and backported to 21.0.4 by printing only when the lock is free. The Loom team said they wanted the property gone, and it was removed in JDK 24.Use JFR's jdk.VirtualThreadPinned event, never the flag, and never time a run with it on.
RejectedExecutionException: Thread limit exceeded replacing blocked worker from runAsync on the common pool at 1,000 tasks (§12).The ForkJoinPool docs say the common pool allows 256 spare threads by default and throws exactly this when a blocked worker can't be replaced. A production report hit the same exception from blocking Redis calls (Lettuce) inside a parallel stream. Guides on CompletableFuture name the default common pool as a production risk for I/O.Never block on the common pool. Always pass an executor to supplyAsync/runAsync.
java.net.http.HttpClient created 100–300 platform threads even when called from virtual threads (§12).On net-dev in 2023 a user reported one extra platform thread per concurrent request. The JDK networking team explained that the client's default executor is a cached thread pool, and suggested passing your own.HttpClient.newBuilder().executor(Executors.newVirtualThreadPerTaskExecutor()). That cut our peak from 182 to 24.
HttpClient 5's default pool (5 per host, 25 total) made 2,000 calls take 8–12 s on every stack (§13).A Spring Boot issue (#48479) calls out the 5/25 defaults for RestClient and is answered with a customizer workaround, not new defaults. A published test found RestClient.create() made parallel calls 4× slower with HttpClient 5 on the classpath. A production guide to HttpClient 5 lists the 5-per-route default and disabled idle eviction as its first two warnings.Always give RestClient/RestTemplate a request factory with a sized pool (§13 snippet).
NoHttpResponseException when the server closed idle keep-alive connections that HttpClient 5 then reused (§13).Apache's HttpClient 5 connection-management guide recommends periodic eviction of idle and expired connections, plus a small validateAfterInactivity, for long-lived applications. Gradle hit the same exception in 2016 after an HttpClient upgrade stopped checking for stale connections.evictIdleConnections(...) and evictExpiredConnections() on the client builder, plus setValidateAfterInactivity on the connection config.
Headers lost on every thread hop without a TaskDecorator, on pools and virtual threads alike (§12, §13).Write-ups describe losing Spring Security's SecurityContext and MDC correlation IDs as soon as calls moved to CompletableFuture on a custom executor, so downstream services didn't know the caller. Guides recommend a TaskDecorator that copies the context in and clears it in finally, warning that forgetting to clear leaks IDs into unrelated requests on pooled threads.The filter + decorator + interceptor in §13, or explicit capture. Clear in finally.
Structured concurrency code broke between JDK 25 and 27 (§9).JEP 533 (JDK 27) replaced FailedException with ExecutionException, and InfoQ warned that code catching the old type must change. JEP 543 then finalized the API in JDK 28 with no changes from JDK 27; JDK 28 is due in March 2027. A backport library brings the final API to JDK 25.Write new experiments against the JDK 27 shape. That's what will ship in 28.
