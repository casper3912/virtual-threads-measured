13. CPU-bound work: summing BigDecimals seven ways

The GET benchmark shows virtual threads where they shine: thousands of tasks that mostly wait. This section is the counterweight. The job never waits: it sums ten million BigDecimals, split into tasks. It runs seven ways, three JDKs on the Windows desktop and JDK 21 in the cloud, so you can see what each strategy does when the only thing that matters is keeping cores busy. MEASURED

The workload

  • 10,000,000 additions per run, always sum.add(x, MathContext(34)) (34 digits, the precision of IEEE decimal128). BigDecimal is immutable, so every addition allocates a new object. The work is pure CPU plus allocation. Nothing blocks.
  • Three task shapes over the same ten million numbers: 10,000 tasks of 1,000 numbers, 100,000 tiny tasks of 100, and 100 large tasks of 100,000. A task sums its slice. The caller then adds up the task results.
  • Inputs are made up front from a fixed seed, so generating random numbers isn't timed and every strategy sums the same values.
  • Timing: three warm-up runs per strategy, then the median of seven, with a System.gc() before each timed run. Every strategy must produce the same total, or the program stops (checksum: {{CPU_SUM}} on every run here).
  • Each run builds a new executor and closes it with try-with-resources. So pool strategies pay to start their threads every run, as a request-scoped executor would.

Machines: the Windows desktop (Intel Core i7-1260P: 4 performance cores with 2 threads each and 8 efficiency cores, 16 logical CPUs; Temurin 21.0.11, Temurin 25.0.5, Corretto 27.0.1) and a 2-vCPU Intel Xeon @ 2.10 GHz Linux container (OpenJDK 21.0.12). The cloud machine is a different instance from the one used elsewhere on this page.

The seven strategies, and what each one does underneath

All seven call the same sumOne(xs), a plain loop over one task's slice. They differ only in which thread runs each task, how a task gets to that thread, and how the partial sums come back.

static BigDecimal sumOne(BigDecimal[] xs) {
    BigDecimal s = BigDecimal.ZERO;
    for (BigDecimal x : xs) s = s.add(x, MC);   // MC = new MathContext(34)
    return s;
}

1 · Sequential for loop: the baseline

BigDecimal total = BigDecimal.ZERO;
for (BigDecimal[] xs : inputs) total = total.add(sumOne(xs), MC);

One thread and two nested loops, nothing else. Its time is the cost of the arithmetic on one core. On the desktop that was {{CPU:desktop:27:loop:10000}} for the 10,000-task shape on JDK 27. Every other row is "how much of this did we spread across cores, minus what spreading it cost". The small speed-up number in the tables is measured against this row from the same run.

The loop also has a hidden advantage: one thread on an otherwise idle machine gets the processor's highest single-core boost clock. Once every core is busy, each core runs slower. That's one reason no strategy below gets close to 16× on 16 logical CPUs. INFERRED

2 · Sequential stream: the same thing, written as a pipeline

Arrays.stream(inputs).map(BigDecimalBench::sumOne).reduce(BigDecimal.ZERO, (a, b) -> a.add(b, MC));

Without .parallel(), a stream runs on the calling thread, one element at a time, in order: the same work as the loop. The pipeline adds a Spliterator, a lambda call per element and a reduce step, but each element carries 100 to 100,000 BigDecimal additions, so the overhead is too small to see once the JIT has inlined it. It's here so the parallel-stream row can be read as "what .parallel() bought", not "what streams bought". Measured: the stream and the loop swapped places from cell to cell, with no consistent winner (see finding 7).

3 · Platform pool, one thread per core

try (var ex = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors())) {
    List<Future<BigDecimal>> fs = new ArrayList<>();
    for (BigDecimal[] xs : inputs) fs.add(ex.submit(() -> sumOne(xs)));
    BigDecimal total = BigDecimal.ZERO;
    for (var f : fs) total = total.add(f.get(), MC);
}

The textbook answer for CPU-bound work. newFixedThreadPool(16) is a ThreadPoolExecutor with 16 OS threads and one LinkedBlockingQueue in front of them. submit() wraps each task in a FutureTask and puts it on the queue. Each worker takes a task, runs it, and takes the next. The main thread then calls get() on every future in order, so the final additions are serial.

When tasks are coarse, this is about as good as it gets: with 10,000 or 100 tasks on the desktop, it was the fastest strategy or within 5% of the fastest on every JDK. When tasks are tiny (100 additions, a few microseconds each), the shared queue becomes the hot spot. All 16 workers take from the same lock-protected queue while the main thread keeps adding to it, and the time each task waits to be handed out grows compared with the time it runs. INFERRED

4 · Platform pool, four threads per core

Executors.newFixedThreadPool(4 * Runtime.getRuntime().availableProcessors())   // 64 on the desktop

The same mechanism with four times the threads. "Cores × N" sizing comes from I/O-bound pools, where extra threads fill the time others spend waiting (Little's law, section 1). Here nothing waits, so the extra threads have no gaps to fill. The OS time-slices 64 runnable threads over 16 logical CPUs, and each switch costs a context switch and the cache contents the previous thread had built up. On the desktop it was slower than one thread per core in every one of the 9 cells. On the noisier 2-vCPU machine it won one cell, lost one and tied the third, so there the difference is within noise.

5 · Platform thread per task (cached pool)

Executors.newCachedThreadPool()

The "one thread per unit of work" model with OS threads. A cached pool hands each task straight to an idle worker through a SynchronousQueue. If no worker is waiting at that instant, it starts a new OS thread, and idle threads live for 60 seconds. With 100 large tasks that's at most 100 threads, which is nothing. With 100,000 tiny tasks the main thread submits far faster than workers come back for more, so the pool starts a stream of new threads, each with an OS call and a stack reservation (about 1 MB by default on 64-bit JDKs).

That cost dominates at 100,000 tasks: {{CPU:desktop:27:cached:100000}} on JDK 27 against {{CPU:desktop:27:vt:100000}} for virtual threads, and on 2 vCPUs it was slower than doing everything on one thread ({{CPU:container:21:cached:100000}} vs {{CPU:container:21:loop:100000}}). This row is the problem virtual threads were built to solve.

6 · Virtual thread per task

Executors.newVirtualThreadPerTaskExecutor()

One virtual thread per task, scheduled onto a ForkJoinPool of carrier threads, one per logical CPU by default (section 2). Starting a virtual thread is a small heap allocation, not an OS call, so 100,000 of them are cheap. The scheduler is work-stealing: each carrier keeps its own deque, and an idle carrier takes work from a busy one, so there's no single shared queue for every task to pass through.

What it can't do here is go faster than the cores. A virtual thread only leaves its carrier when it blocks. The JDK doesn't time-slice virtual threads, and a BigDecimal loop never blocks, so each task holds one of the 16 carriers until it's done. That's the same 16-way parallelism as strategy 3, with a different way of handing out tasks. Across all 12 cells, virtual threads were {{CPU_VT_VS_POOL}} compared with the pool sized to the cores. They pulled ahead with 100,000 tiny tasks on the desktop on JDK 25 and 27, which fits the queue explanation in strategy 3, but this benchmark doesn't isolate the cause. INFERRED

Because nothing yields, CPU-heavy virtual threads also hold their carriers away from any I/O-bound virtual threads in the same JVM. Keep long CPU work off the default scheduler in a service that depends on it for request handling. INFERRED

7 · Parallel stream

Arrays.stream(inputs).parallel().map(BigDecimalBench::sumOne).reduce(BigDecimal.ZERO, (a, b) -> a.add(b, MC));

Runs on the shared ForkJoinPool.commonPool(), whose parallelism is one less than the CPU count, and the calling thread works too. Instead of submitting each task, the stream splits the array range in half, again and again, into a tree of ForkJoinTasks. Each fork goes on the forking worker's own deque, and idle workers steal the largest pieces first. Partial sums are combined in pairs as the tree folds back up, so no single thread adds 100,000 results at the end, and nothing creates a Future per element.

That's why it was the fastest strategy for 100,000 tiny tasks on every machine and JDK. The cost is control. The common pool is shared by everything in the JVM that uses it (other parallel streams, and CompletableFuture stages run without an executor), and blocking on it can fail outright (GET finding 6). It's a good fit for a batch job or a self-contained computation. In a server, a dedicated pool gives you isolation. INFERRED

What the numbers say

  1. Spreading the work helps, but nowhere near 16×. The best strategy beat the loop by {{CPU_BEST:desktop}} on the 16-thread desktop ({{CPU_BEST:desktop:nov5}} in the November 5 run). Only 4 of the 12 cores have a second hardware thread, the 8 efficiency cores are slower, all-core clocks are lower than the single-core boost, and every addition allocates, which loads the memory system and the garbage collector. MEASURED INFERRED (the causes)
  2. Two cores are two cores. On the 2-vCPU machine the best strategy reached {{CPU_BEST:container}}, close to the ideal 2×. MEASURED
  3. Virtual threads don't speed up CPU work, and don't slow it down much either. Against a pool sized to the cores, virtual threads were {{CPU_VT_VS_POOL}}. With 10,000 tasks on JDK 27 both took {{CPU:desktop:27:vt:10000}}. That matches Lab 3, at a larger scale and on more cores. MEASURED
  4. With tiny tasks, how work is handed out decides the result. At 100,000 tasks of 100 numbers on JDK 27: parallel stream {{CPU:desktop:27:pstream:100000}}, virtual threads {{CPU:desktop:27:vt:100000}}, core-sized pool {{CPU:desktop:27:fixed:100000}}, thread per task {{CPU:desktop:27:cached:100000}}. On the desktop, on every JDK, the two work-stealing strategies (parallel stream, virtual threads) were at least as fast as one shared queue (the pool), and much faster than a new OS thread per task. On 2 vCPUs, with only two carriers to steal between, the pool beat virtual threads ({{CPU:container:21:fixed:100000}} vs {{CPU:container:21:vt:100000}}). MEASURED
  5. Platform thread per task is the outlier, and the reason virtual threads exist. At 100,000 tasks it was at least 1.5× slower than virtual threads on every machine and JDK ({{CPU:desktop:21:cached:100000}} vs {{CPU:desktop:21:vt:100000}} on JDK 21), and on 2 vCPUs slower than the plain loop. Same programming model, very different cost. MEASURED
  6. More threads than cores only adds switching. On the desktop, 64 threads was slower than 16 in all 9 cells, for example {{CPU:desktop:25:fixed4:100000}} vs {{CPU:desktop:25:fixed:100000}} at 100,000 tasks on JDK 25. Size CPU pools to the cores. MEASURED
  7. A sequential stream is a for loop. Its time ranged {{CPU_STREAM_RANGE}} of the loop's in the same run, and it was faster in some cells and slower in others. Streams don't parallelize anything until you ask. MEASURED
  8. Don't compare JDK versions from these tables. The same loop took {{CPU:desktop:21:loop:10000}}, {{CPU:desktop:25:loop:10000}} and {{CPU:desktop:27:loop:10000}} on JDK 21, 25 and 27 run minutes apart, and {{CPU:desktop:27:loop:10000:nov5}} on JDK 27 three days earlier. For CPU-bound work:
  • Use a parallel stream for a self-contained computation, or a ForkJoinPool or fixed pool sized to availableProcessors() when you need isolation from the rest of the JVM.
  • Make tasks coarse enough that handing them out is cheap compared with running them. 1,000 additions per task was plenty here; 100 was where dispatch started to show.
  • Virtual threads are fine when code is already written thread-per-task, but don't expect a speed-up. In a service, keep long CPU work off the virtual-thread scheduler so it doesn't hold carriers away from request handling.
  • Never give CPU-bound work more platform threads than cores, and never start one OS thread per small task.
